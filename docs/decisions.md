# 架构与产品决策记录

这里只记录已经明确接受的方向。研究建议、临时想法和未验证技术不得直接写成“已决定”。

## 已决定

### D001：游戏采用《熊出没》多世界/多时期主线结构

状态：已接受

不同动画时期/系列作为不同世界或章节，世界观、角色、场景和机制随时间推进。

熊大、熊二、光头强的长期关系主线为：

```text
对立
→ 偶尔停战
→ 暂时联手
→ 建立信任
→ 真正友谊
```

准确官方顺序与角色首次登场仍需资料核验后补充。

### D002：核心玩法采用“PVZ 路线塔防 + 熊出没原创机制”

状态：已接受

保留易理解的路线防守、格子部署、资源与波次逻辑，但不做单纯换皮。

### D003：美术方向为 Q 版夸张搞笑

状态：已接受

角色形象需要保持辨识度，同时通过动作、表情、互动、胜负演出体现《熊出没》的喜剧感。

### D004：第一阶段规模为一个完整小世界

状态：已接受

目标：

- 10 关
- 8 名可用角色
- 6 种普通/精英敌人
- 1 个 Boss
- 1 套完整 UI
- 1 条完整小世界剧情

### D005：角色战场合成是核心系统

状态：已接受

游戏必须支持同角色合成升级，并将其作为战斗中的重要策略来源。

### D006：同角色升级优先改变行为而非只加数值

状态：已接受

例如角色升级后可改变连击次数、攻击范围、控制方式、弹道、节奏或表现。

### D007：支持指定跨角色融合

状态：已接受

不同角色可以按预定义配方融合，结果必须体现双方能力“合二为一”。

跨角色融合优先表现为协作形态、组合机关或共同战术，而不是强行把角色变成违和的新生物。

### D008：融合配方与人物关系可以绑定

状态：已接受

敌对时期不能使用的组合，可在剧情关系发展后解锁。

### D009：不要求所有角色两两融合

状态：已接受

优先少量高质量专属配方，控制组合数量与制作成本。

### D010：羁绊优先做机制联动

状态：已接受

羁绊尽量通过协同攻击、保护、资源、控制、机关联动等行为体现，避免只做“攻击 +10%”式加成。

### D011：不同世界必须有独有玩法机制

状态：已接受

春、夏、秋、冬、森林、小镇、探险、微观等世界不能只是换背景，必须至少包含一个影响战斗决策的世界机制。

### D012：关卡不只允许单一“守到最后”目标

状态：已接受

可以穿插护送、保护、收集、解谜、坚守时间、Boss 特殊战等目标，避免 10 关重复体验。

### D013：角色存在局内成长与局外成长

状态：已接受

- 局内：合成、融合、临时强化，过关后重置。
- 局外：解锁角色、配方、技能变体、世界、图鉴和表现内容。

### D014：游戏前端围绕世界地图/时间轴与战斗直觉设计

状态：已接受

主界面优先表现为狗熊岭/不同世界的旅程地图；战斗 UI 需要清晰支持拖拽部署、合成目标与结果预览。

### D015：当前先做产品定义、研究和 PoC，不直接大规模开发

状态：已接受

先定玩法、世界、角色、UI 和技术路线；关键方案经过独立研究和 PoC 再进入正式实现。

### D016：Agent 分工明确

状态：已接受

- 用户：产品负责人 / 总策划。
- GPT-5.6 Sol：游戏总监、美术总监、技术评审。
- Work + Sol：研究负责人。
- Hermes + Ox Alpha：主程 / 执行负责人。
- Codex：第二程序员 / Code Review / PoC 负责人。

默认 Hermes 实现、Codex 评审/PoC，避免两者同时大规模修改同一模块。

### D017：GitHub 文档是统一事实源

状态：已接受

- `AGENTS.md`：角色分工与工作规则
- `docs/product.md`：产品定义
- `docs/architecture.md`：模块边界与技术候选
- `docs/decisions.md`：已接受决定
- `docs/project-plan.md`：阶段计划与任务分配
- `docs/research/`：研究证据与独立报告

### D018：World 01 采用经典狗熊岭早期守林冲突

状态：已接受

第一世界采用早期“熊大、熊二守护森林 vs. 伐木工光头强”的关系阶段。

World 01 不逐集复刻动画，而是在该关系状态下编写原创 10 关小剧情。关末光头强仍是对手，不提前跳到后期稳定合作关系。

详细方案见 `docs/design/world-01-classic-forest.md`。

### D019：World 01 同角色升级最高三级

状态：已接受

World 01 首版使用：

```text
I → II → III
```

每级优先改变行为、攻击方式、控制、范围、节奏或表现，不做纯数值升级。

### D020：World 01 首批跨角色融合只做两组

状态：已接受

首批固定配方：

- 熊大 + 熊二 → `兄弟阵线`
- 吉吉 + 毛毛 → `猴王连携`

融合结果固定、可预览，并必须存在覆盖或功能上的机会成本。

### D021：World 01 首版使用单资源

状态：已接受

部署、同角色升级和固定融合先共用一种资源。暂定显示名为“森林物资”。

只有灰盒 PoC 证明单资源无法有效控制融合滚雪球时，才重新评估双资源。

### D022：棋盘采用 5 路，列数参数化

状态：已接受

- 固定 5 条路线。
- 列数由配置决定，不允许核心逻辑写死 9。
- 第一轮视觉和关卡原型默认按 5×9 参考。

### D023：World 01 世界机制采用“伐木标记/保护树木”

状态：已接受

部分树木占用格子并作为需要保护的目标，特定敌人和 Boss 阶段可直接威胁这些目标，使“保护森林”进入实际胜负规则。

### D024：World 01 使用 6 类原创 Q 版伐木机关敌人

状态：已接受

首批行为类型：

1. 标准基础单位；
2. 高速低耐久；
3. 正面高防御；
4. 缓慢高耐久；
5. 越障；
6. 远程限制角色行动。

角色表现采用本项目原创机关，不宣称为动画原作机器。

### D025：World 01 Boss 为早期光头强

状态：已接受

Boss 使用三阶段结构：

1. 光头强亲自操作小机关；
2. 大型伐木车；
3. 李老板催促后进入高压阶段，同时攻击被标记树木。

Boss 依靠阶段、路线、机关和目标变化制造压力，不做纯血量墙。

### D026：肥波在 World 01 属于光头强一侧，不作为友方常驻卡

状态：已接受

央视公开节目简介可确认肥波是光头强的宠物猫，并存在跟随/帮助光头强行动的情节。因此早期世界不把肥波写成熊大熊二一方的常驻友军。

World 01 的第 8 名友方可用角色继续核验，不为了凑人数提前塞入明显属于后续时期的角色。

### D027：World 01 灰盒 PoC 不使用原作素材

状态：已接受

Codex PoC 全部使用原创几何占位物和功能代号。正式角色 Q 版视觉设计与玩法验证并行，但不能阻塞 PoC。

### D028：正式技术栈采用 Godot 4.7.2 + GDScript

状态：已接受

基于 P1 灰盒 PoC 的 Windows、5 路参数化棋盘、拖拽、固定路线、数据化规则与 headless 验证结果，第一版正式开发采用：

```text
Godot 4.7.2
+ GDScript
```

P1 灰盒代码是技术证据和参考实现，不等于可以无审查地直接演化成正式架构。正式实现仍需遵守 `docs/architecture.md` 的模块边界与数据驱动原则。

### D029：正式自动测试默认采用 GUT 9.7.1

状态：已接受

P1 对 GUT 9.7.1 与 GdUnit4 6.2.0 使用同一组 8 项规格进行 Windows/headless 对照，两者均通过。当前项目以 GDScript 规则、配方和状态边界测试为主，GUT 的 headless 调用、退出码与 CI 链路更直接，因此第一版默认采用 GUT 9.7.1。

若后续出现大量复杂场景/UI/InputEvent 自动化需求，可针对真实场景重新评估 GdUnit4，但不得无理由同时长期维护两套测试框架。

### D030：项目进入 P2 正式实现阶段

状态：已接受

P0 研究、World 01 主体设计与 P1 灰盒 PoC 已完成并通过评审。后续默认分工：

- Hermes + Ox Alpha：正式工程骨架与主实现；
- Codex：独立 Code Review、专项 PoC 与难问题验证；
- GPT-5.6 Sol：产品、架构、美术和 PR 验收；
- 用户：最终产品判断与试玩反馈。

第一目标是 Playable Prototype，不直接扩写完整 10 关内容。
