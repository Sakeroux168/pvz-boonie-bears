## H1｜正式项目骨架

建立或整理以下职责边界，具体目录名可微调，但职责不能混乱：

```text
src/
  app/
  data/
  battle/
  grid/
  units/
  enemies/
  fusion/
  world_rules/
  resources/
  abilities/
  ui/
  narrative/
  save/
  tests/
assets/
  placeholders/
```

要求：

- UI 不计算核心战斗规则。
- 战斗规则尽量可在 headless 下测试。
- 角色、敌人、关卡、配方不得依赖巨大 if/else 表。
- 列数参数化，5 路固定；默认参考 5×9，但核心逻辑不得写死 9。
- 正式数据定义必须与 PoC 的 `const UNIT_DEFINITIONS` / `const RECIPES` 解耦，至少先建立清晰的数据加载接口。
- 暂时允许 JSON / Resource 等简单格式，但请在 PR 中说明选择、优缺点和未来迁移成本；不要擅自把存档格式永久锁死。

## H2｜最小可玩战斗

只做占位图和功能代号，至少包含：

- 1 张正式结构的测试地图；
- 5 条路线，可配置列数；
- 2 个友方占位角色：A（远程）、B（前排）；
- 2 个敌人：基础敌人、至少一个行为不同的特殊敌人；
- 单资源；
- 可选卡/拖拽部署；
- 基础攻击与承伤；
- 最小波次系统；
- 一次性路线保险；
- 胜利与失败状态；
- 一个 `protected_tree` 类目标，至少能进入关卡胜负条件。

验收时必须能从启动游戏开始完整打一局并正常胜/负，不允许只靠测试代码证明“理论可用”。

## H3｜合成核心

正式实现：

```text
A1 + A1 → A2
A2 + A2 → A3
A1 + B1 → AB
```

要求：

- 同角色升级改变至少一种行为，不只加攻击数值；
- 合成后不能免费满血/清空技能冷却；
- 固定配方，结果不可随机；
- `AB` 必须体现远程 + 前排的协作行为，不做简单数值相加；
- 融合前 UI 能明确显示合法/非法目标与结果预览；
- 融合后两格压成一格，保留明确的横向覆盖机会成本；
- 预留撤销/拆分接口，但本轮不要求完成最终规则；
- 配方规则可由数据层查询，不写角色 ID if/else 链。

## GUT 自动测试

正式阶段只保留 GUT 9.7.1 作为默认测试框架；GdUnit4 对照代码/下载链不应继续成为正式运行必需依赖。

至少覆盖：

1. 5 路与 8/9/10 列配置；
2. 占格冲突；
3. 资源不足拒绝部署；
4. 敌人同路推进；
5. 路线保险只触发一次；
6. `A1+A1→A2`；
7. `A2+A2→A3`；
8. 非法升级/配方拒绝；
9. `A+B→AB`；
10. 合成状态继承，不免费刷新；
11. `protected_tree` 占格、受击和目标条件；
12. 一局胜利/失败状态机的核心规则。

要求 Windows + headless 一键运行，失败必须返回非 0 退出码。
